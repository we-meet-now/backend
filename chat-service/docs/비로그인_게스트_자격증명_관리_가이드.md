# 비로그인 게스트 UUID·토큰 관리 가이드

이 문서는 비로그인 사용자의 게스트 세션을 발급하고, 채팅방 API에서 사용하며, 만료 시 갱신하거나 폐기하는 방법을 설명합니다. 로컬 기본 주소는 다음과 같습니다.

| 서비스 | 주소 |
|---|---|
| Auth | `http://localhost:6112` |
| Chat | `http://localhost:6113` |

실행 환경에서 포트나 API Gateway 주소가 다르면 실제 주소로 바꿔 요청하세요.

```javascript
const authBase = "http://localhost:6112";
const chatBase = "http://localhost:6113";
```

프런트엔드에서 guestToken·브라우저 쿠키를 사용해 목록, 채팅 내역, 입장, STOMP 메시지 흐름을 직접 확인하려면 [프런트엔드 게스트 채팅 API 테스트 가이드](프런트엔드_게스트_채팅_API_테스트_가이드.md)를 참고하세요.

## 권장 운영 흐름 (5단계)

1. **첫 접속/설치:** 게스트 identity와 인증 자격증명을 발급합니다.
2. **웹 브라우저 저장:** `guest_session` 불투명 세션 ID를 `HttpOnly; Secure` 쿠키로 저장합니다. 브라우저 JavaScript는 UUID나 토큰을 읽지 않습니다.
3. **모바일 앱 저장:** 네이티브 앱은 짧은 만료의 `guestToken`과 별도 `refreshToken`을 사용합니다. refreshToken은 iOS Keychain 또는 Android Keystore에 보관합니다. 이 단계는 운영 방식만 기록하고, 이번 변경에서 모바일 앱 저장 코드나 별도 API는 개발하지 않습니다. 기존 Auth 발급/갱신 API를 사용합니다.
4. **API 요청:** 서버는 브라우저 쿠키 또는 Authorization 토큰으로 사용자를 식별하고, UUID는 Auth 서버가 세션/토큰에서 확인합니다. Chat API 요청 URL이나 본문에 UUID를 넣지 않습니다.
5. **만료 갱신:** guestToken이 만료되면 현재 refreshToken으로 Auth API를 호출합니다. Auth는 새 guestToken과 새 refreshToken을 발급하고 DB의 저장 hash를 교체해 이전 refreshToken을 즉시 무효화합니다. 브라우저 세션은 HttpOnly 쿠키 회전 API를 사용합니다.

## 1. UUID와 토큰의 역할

| 값 | 역할 | 보관·사용 방법 |
|---|---|---|
| `uuId` | 게스트 사용자 식별자 | 발급 응답에 포함될 수 있지만 Chat API 요청에는 보내지 않습니다. 서버가 guestToken claim 또는 브라우저 세션에서 확인 |
| `guestToken` | Chat API 요청 인증용 단기 토큰 | `Authorization: Bearer <guestToken>` 헤더로 전달. 약 30분 후 만료 |
| `refreshToken` | 새 `guestToken` 발급용 장기 비밀값 | refresh API에만 JSON body로 전달. 일반 Chat API에는 보내지 않음 |
| `guest_session` 쿠키 | 브라우저용 불투명한 세션 ID | 서버만 읽을 수 있는 `HttpOnly` 쿠키. 브라우저 코드에서 UUID나 토큰을 읽고 보관하지 않음 |

`guestToken`에는 게스트 UUID가 연결되어 있으며, Auth 서버가 토큰의 UUID를 DB의 사용자와 대조합니다. 클라이언트는 Chat API에 UUID를 따로 전달할 필요가 없습니다. UUID만으로는 기존 게스트의 토큰을 복구하거나 갱신할 수 없습니다.

`refreshToken`은 갱신할 때마다 회전합니다. 성공 응답을 받으면 새 `guestToken`과 새 `refreshToken`을 함께 저장하고 기존 refreshToken을 더 이상 사용하지 마세요. refreshToken은 30일 미사용 시 만료되며, 발급 후 최대 유효 기간은 180일입니다. 응답의 `refreshTokenExpiresAt`은 유휴 만료 시각입니다.

## 2. 권장 요청 흐름

### 2.1 첫 방문: 새 게스트 세션 생성

`POST /api/auth/v1/users/no-login/guest-sessions`를 인증 헤더나 요청 본문 없이 호출합니다.

```http
POST http://localhost:6112/api/auth/v1/users/no-login/guest-sessions
```

성공 응답은 HTTP `201`, `statusCode: "2000"`입니다. 예시의 토큰 값은 설명용 placeholder이며 실제 값이 아닙니다.

```json
{
  "statusCode": "2000",
  "data": {
    "uuId": "<발급된 UUID>",
    "guestToken": "<발급된 guestToken>",
    "refreshToken": "<발급된 refreshToken>",
    "guestTokenExpiresInSeconds": 1800,
    "refreshTokenExpiresAt": "<ISO-8601 timestamp>"
  },
  "message": "게스트 세션 생성 성공"
}
```

응답에는 `Cache-Control: no-store`가 설정됩니다. 클라이언트에서도 응답 본문을 로그, 분석 도구, 오류 추적 서비스에 기록하지 마세요.

### 2.2 4단계: API 요청 (채팅방 목록)

`GET /api/chat/v1/chat-rooms`에 guestToken만 Authorization 헤더로 보냅니다. UUID는 URL이나 요청 본문에 포함하지 않습니다.

```http
GET http://localhost:6113/api/chat/v1/chat-rooms
Authorization: Bearer <같은 세션의 guestToken>
```

성공하면 HTTP `200`, `statusCode: "2000"`이 반환됩니다. 참여한 채팅방이 없더라도 인증이 성공하면 `data.chatRoomList`가 빈 배열일 수 있습니다.

### 2.3 5단계: guestToken 만료 시 갱신 및 비밀값 회전

guestToken이 만료되면 저장한 refreshToken만 Auth API에 보냅니다. Authorization 헤더나 UUID는 보내지 않습니다. 백엔드는 refreshToken 원문이 아닌 SHA-256 hash를 DB에 저장하고, 갱신 요청 시 활성 세션 row를 잠근 뒤 만료 여부를 검증합니다. 성공하면 새 guestToken과 새로운 무작위 refreshToken을 발급하고 같은 row의 hash를 교체합니다. 이전 refreshToken hash는 더 이상 저장되지 않으므로 이전 값은 즉시 사용할 수 없습니다.

```http
POST http://localhost:6112/api/auth/v1/users/no-login/guest-sessions/refresh
Content-Type: application/json
```

```json
{
  "refreshToken": "<현재 저장된 refreshToken>"
}
```

성공 응답은 HTTP `200`, `statusCode: "2000"`입니다. 응답의 UUID는 기존 게스트 UUID와 같고 `guestToken`, `refreshToken`은 새 값입니다. 새 두 값을 안전하게 저장한 뒤 다음 요청부터 사용하세요. 이전 refreshToken으로 다시 갱신하면 HTTP `401`이어야 합니다.

프런트엔드에서는 갱신 요청이 성공한 뒤에만 두 값을 함께 교체합니다.

```javascript
const refreshResponse = await fetch(
  `${authBase}/api/auth/v1/users/no-login/guest-sessions/refresh`,
  {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ refreshToken })
  }
);

if (!refreshResponse.ok) {
  throw new Error(`Guest token refresh failed: ${refreshResponse.status}`);
}

const { guestToken: nextGuestToken, refreshToken: nextRefreshToken } =
  (await refreshResponse.json()).data;
// 둘 다 안전하게 교체한 뒤, 다음 Chat 요청에 nextGuestToken을 사용합니다.
```

여러 탭이나 요청이 동시에 refresh API를 호출하지 않도록 갱신을 단일화하세요. 동시 갱신은 한 요청만 성공하고 나머지 요청은 이전 refreshToken을 사용하게 만들 수 있습니다.

### 2.4 세션 폐기

로그아웃 등으로 세션을 폐기하려면 현재 refreshToken을 보냅니다.

```http
POST http://localhost:6112/api/auth/v1/users/no-login/guest-sessions/revoke
Content-Type: application/json
```

```json
{
  "refreshToken": "<현재 저장된 refreshToken>"
}
```

폐기 성공은 HTTP `200`입니다. 이후 해당 refreshToken으로 갱신하면 HTTP `401`이 반환됩니다. 폐기 후 클라이언트에서도 UUID와 토큰을 삭제하세요.

### 2.5 Chat REST/STOMP 요청 예시

모바일 앱은 guestToken을 Authorization 헤더에만 보내고, UUID는 URL·query parameter·request body에 보내지 않습니다. 서버가 guestToken의 UUID claim을 Auth DB와 대조해 사용자를 식별합니다.

```javascript
const response = await fetch(`${chatBase}/api/chat/v1/chat-rooms`, {
  headers: {
    Authorization: `Bearer ${guestToken}`
  }
});
```

브라우저는 HttpOnly 세션 쿠키를 사용하며 Authorization 헤더와 UUID를 보내지 않습니다.

```javascript
const response = await fetch(`${apiBase}/api/chat/v1/chat-rooms`, {
  credentials: "include"
});
```

채팅방 내역 조회는 `GET /api/chat/v1/chat-rooms/roomId={roomId}`, 입장/읽음 처리는 `POST /api/chat/v1/chat-rooms/enter-room`을 사용합니다. 두 요청도 인증 정보는 동일하게 Authorization token 또는 브라우저 쿠키로 전달하며, `enter-room` 본문에는 `roomId`만 포함합니다.

STOMP 연결은 모바일에서 CONNECT의 Authorization 헤더로 guestToken을 보내고, 브라우저에서는 동일 호스트 쿠키를 사용합니다. `chat.sendMessage`와 `chat.addUser` 메시지 본문에는 `chatRoomId`, `message`, `chatType`만 보내며 `uuId`나 `userId`는 보내지 않습니다. 서버는 인증된 Principal의 사용자 ID로 메시지를 저장합니다.

## 3. 브라우저에서 HttpOnly 세션 쿠키 사용

브라우저에서는 UUID, guestToken, refreshToken을 JavaScript 저장소에 보관하는 대신 Auth 서비스가 발급하는 `guest_session` 쿠키를 사용합니다. Auth 서비스는 쿠키 값의 SHA-256 해시만 DB에 저장하고, 해당 해시에서 게스트 사용자를 찾습니다. UUID나 세션 ID 원문은 발급 응답 본문에 포함되지 않습니다.

### 필수 도메인 구성

이 방식은 프런트와 API가 동일 사이트여야 합니다. 예를 들어 프런트는 `https://app.example.com`, API Gateway는 `https://api.example.com`으로 구성하세요. 쿠키는 `api.example.com` host-only로 설정되며, Auth와 Chat 요청은 모두 같은 `api.example.com` 주소의 Gateway를 통해 보내야 합니다. 쿠키에 `Domain` 속성을 지정하지 않아 다른 호스트로 불필요하게 공유하지 않습니다.

현재 `*.vercel.app` 프런트에서 `*.onrender.com` API를 직접 호출하는 구성은 cross-site이므로 `SameSite=Lax` 쿠키가 전송되지 않습니다. `app.example.com`과 `api.example.com` 같은 커스텀 도메인을 연결한 뒤 API Gateway, Auth, Chat의 `FRONT_URL`에 실제 프런트 Origin을 설정해야 브라우저에서 이 세션 방식을 사용할 수 있습니다. Auth와 Chat 요청 모두 API Gateway의 같은 공개 호스트로 보내세요. 로컬에서는 `localhost` 프런트와 Auth/Chat 포트를 사용할 수 있습니다.

### 현재 배포 주소를 대입한 예시

현재 프런트와 서비스별 Swagger 주소는 다음과 같습니다.

| 구분 | 주소 |
|---|---|
| 프런트 | `https://front-azure-iota.vercel.app/` |
| Auth Swagger UI | `https://backend-auth-service-dev.onrender.com/api/auth/v1/swagger-ui/index.html` |
| Chat Swagger UI | `https://backend-chat-service-new.onrender.com/api/chat/v1/swagger-ui/index.html` |

서비스에 직접 요청하는 주소는 Auth의 `https://backend-auth-service-dev.onrender.com/api/auth/...`와 Chat의 `https://backend-chat-service-new.onrender.com/api/chat/...`입니다. 이 두 Render 호스트는 서로 다르고 Vercel 프런트와도 cross-site입니다. 따라서 Auth에서 발급한 `guest_session` 쿠키는 Auth 호스트에만 저장되어 Chat 호스트로 전송되지 않습니다. `SameSite=None; Secure`만으로는 서로 다른 호스트 간 쿠키 공유가 해결되지 않으며, `Domain=onrender.com`으로 설정하는 방식도 사용하면 안 됩니다.

즉, 아래처럼 각 Render 서비스를 직접 호출하는 코드는 현재 `guest_session` 쿠키 방식으로 Chat 인증까지 이어지지 않습니다.

```javascript
const authBase = "https://backend-auth-service-dev.onrender.com";
const chatBase = "https://backend-chat-service-new.onrender.com";

await fetch(`${authBase}/api/auth/v1/users/no-login/guest-browser-sessions`, {
  method: "POST",
  credentials: "include"
});

// 서로 다른 Render 호스트이므로 Auth에서 받은 guest_session 쿠키가 이 요청에는 포함되지 않습니다.
const rooms = await fetch(`${chatBase}/api/chat/v1/chat-rooms`, {
  credentials: "include"
});
```

브라우저 쿠키 흐름을 사용하려면 Vercel 프로젝트에 `https://app.<소유 도메인>` 같은 프런트 커스텀 도메인을 연결하고, API Gateway에도 같은 소유 도메인의 `https://api.<소유 도메인>`을 연결하세요. Gateway에서 `/api/auth/**`는 Auth Render 서비스로, `/api/chat/**`는 Chat Render 서비스로 라우팅합니다. 브라우저는 두 서비스를 직접 호출하지 않고 아래처럼 Gateway의 **같은 공개 호스트**를 호출합니다.

```javascript
const apiBase = "https://api.<소유 도메인>";

await fetch(`${apiBase}/api/auth/v1/users/no-login/guest-browser-sessions`, {
  method: "POST",
  credentials: "include"
});

const rooms = await fetch(`${apiBase}/api/chat/v1/chat-rooms`, {
  credentials: "include"
});
```

프런트와 API가 동일 사이트의 sibling subdomain이어야 `SameSite=Lax`가 적용됩니다. Gateway, Auth, Chat의 `FRONT_URL`은 실제 프런트 커스텀 Origin(예: `https://app.<소유 도메인>`)으로 설정하세요. 운영 Swagger UI도 Gateway를 통해 노출한다면 동일하게 `https://api.<소유 도메인>/api/auth/v1/swagger-ui/index.html`과 `https://api.<소유 도메인>/api/chat/v1/swagger-ui/index.html` 주소를 사용해 cookie 흐름을 테스트하세요. 위 표의 서비스별 Swagger 주소는 API 문서 확인에는 쓸 수 있지만, 서로 다른 호스트를 직접 호출하는 cookie 통합 테스트에는 사용할 수 없습니다.

쿠키 속성은 `HttpOnly; Secure; SameSite=Lax; Path=/`이며, Secure는 기본 활성화입니다. 브라우저 요청에는 credential 포함 설정이 필요합니다. CORS는 허용된 프런트 Origin을 정확히 등록해야 하며 `Access-Control-Allow-Origin: *`와 credential을 함께 사용할 수 없습니다.

Auth와 Chat 서비스에는 동일한 `GUEST_BROWSER_SESSION_INTERNAL_SECRET` 환경 변수를 설정하세요(최소 32자 이상의 무작위 값 권장). Chat은 이 키를 Auth의 내부 세션 확인 요청에만 사용합니다. 두 Render 서비스의 환경 변수에 같은 값을 등록하고 코드, 프런트엔드, API 응답, 로그에는 포함하지 마세요. 설정하지 않으면 브라우저 쿠키를 이용한 Chat 요청은 실패합니다.

### 브라우저 세션 생성

`POST /api/auth/v1/users/no-login/guest-browser-sessions`를 호출합니다. 요청 본문은 필요하지 않습니다. 프런트 응답에는 만료 시각만 있으며 UUID, 세션 ID, guestToken, refreshToken은 포함되지 않습니다. 응답 `Set-Cookie` 헤더의 쿠키는 JavaScript에서 읽을 수 없고, 같은 사이트의 이후 API 요청에 브라우저가 자동으로 첨부합니다.

```javascript
await fetch("https://api.example.com/api/auth/v1/users/no-login/guest-browser-sessions", {
  method: "POST",
  credentials: "include"
});
```

### 브라우저에서 채팅방 목록 조회

`GET /api/chat/v1/chat-rooms`를 `credentials: "include"`로 호출합니다. 브라우저 세션 방식에서는 `uuid` query parameter와 `Authorization` 헤더를 보내지 않습니다. Chat 서비스는 쿠키를 Auth 서비스에 전달하고, Auth가 세션 ID에서 UUID와 사용자 ID를 찾아 응답합니다.

```javascript
const response = await fetch("https://api.example.com/api/chat/v1/chat-rooms", {
  credentials: "include"
});
```

성공은 HTTP `200`, `statusCode: "2000"`입니다. 만료되었거나 유효하지 않은 쿠키는 HTTP `401`입니다.

### 세션 회전 및 폐기

세션을 명시적으로 회전할 때는 다음 API를 호출하세요. 요청 본문이나 Authorization 헤더는 필요하지 않습니다. 성공 시 기존 세션 ID가 폐기되고 새 HttpOnly 쿠키가 설정됩니다.

```javascript
await fetch("https://api.example.com/api/auth/v1/users/no-login/guest-browser-sessions/refresh", {
  method: "POST",
  credentials: "include"
});
```

세션 폐기 요청은 다음과 같습니다. 성공 시 브라우저 쿠키도 삭제됩니다.

```javascript
await fetch("https://api.example.com/api/auth/v1/users/no-login/guest-browser-sessions/revoke", {
  method: "POST",
  credentials: "include"
});
```

브라우저 세션은 30일 미사용 시 만료되고 발급 후 최대 180일까지만 유효합니다. 채팅방 조회 시 서버가 유휴 만료 시각을 갱신합니다. 180일 절대 만료 후에는 새 세션을 생성해야 하며, 새 세션은 새 게스트 identity입니다.

Auth의 `/guest-browser-sessions/resolve` 경로는 Chat 서비스가 쿠키를 검증하기 위해 호출하는 경로입니다. 프런트에서 직접 호출하거나 응답의 UUID를 저장하지 마세요.

## 4. Postman으로 발급·조회·갱신 테스트

### 환경 변수 준비

Postman Environment에 아래 변수를 추가하세요.

| 변수 | 초기값 |
|---|---|
| `authBase` | `http://localhost:6112` |
| `chatBase` | `http://localhost:6113` |
| `uuid` | 비워 둠 |
| `guestToken` | 비워 둠 |
| `refreshToken` | 비워 둠 |
| `previousRefreshToken` | 비워 둠 |

### 요청 1: 게스트 세션 생성

- Method: `POST`
- URL: `{{authBase}}/api/auth/v1/users/no-login/guest-sessions`
- Body: 없음

Tests 탭에서 UUID와 토큰을 환경 변수에 저장합니다.

```javascript
const response = pm.response.json();

pm.test("게스트 세션이 생성됨", () => {
  pm.response.to.have.status(201);
  pm.expect(response.statusCode).to.eql("2000");
});

pm.environment.set("uuid", response.data.uuId);
pm.environment.set("guestToken", response.data.guestToken);
pm.environment.set("refreshToken", response.data.refreshToken);
```

### 요청 2: 게스트 채팅방 목록 조회

- Method: `GET`
- URL: `{{chatBase}}/api/chat/v1/chat-rooms`
- Header: `Authorization` = `Bearer {{guestToken}}`

Tests 예시:

```javascript
const response = pm.response.json();

pm.test("채팅방 목록 조회 성공", () => {
  pm.response.to.have.status(200);
  pm.expect(response.statusCode).to.eql("2000");
  pm.expect(response.data.chatRoomList).to.be.an("array");
});
```

### 요청 3: refreshToken 갱신

- Method: `POST`
- URL: `{{authBase}}/api/auth/v1/users/no-login/guest-sessions/refresh`
- Header: `Content-Type` = `application/json`
- Body (raw / JSON):

```json
{
  "refreshToken": "{{refreshToken}}"
}
```

Pre-request Script에서 기존 refreshToken을 테스트용으로 잠시 보관합니다.

```javascript
pm.environment.set("previousRefreshToken", pm.environment.get("refreshToken"));
```

Tests 탭에서 성공과 토큰 회전을 확인하고 새 토큰을 저장합니다.

```javascript
const response = pm.response.json();

pm.test("토큰이 회전됨", () => {
  pm.response.to.have.status(200);
  pm.expect(response.statusCode).to.eql("2000");
  pm.expect(response.data.refreshToken).to.not.eql(
    pm.environment.get("previousRefreshToken")
  );
});

pm.environment.set("uuid", response.data.uuId);
pm.environment.set("guestToken", response.data.guestToken);
pm.environment.set("refreshToken", response.data.refreshToken);
```

### 요청 4: 이전 refreshToken 재사용 거부 확인

요청 3을 성공시킨 뒤 refresh API를 다시 호출하되 Body에 `{{previousRefreshToken}}`을 입력합니다.

```json
{
  "refreshToken": "{{previousRefreshToken}}"
}
```

기대 결과는 HTTP `401`입니다. 테스트 후에는 새로 저장된 `refreshToken`을 계속 사용하세요.

### 요청 5: 선택적으로 세션 폐기

`POST {{authBase}}/api/auth/v1/users/no-login/guest-sessions/revoke`에 현재 `{{refreshToken}}`을 body로 보내면 HTTP `200`이어야 합니다. 폐기한 refreshToken으로 refresh API를 호출하면 HTTP `401`이어야 합니다.

### Postman에서 브라우저 쿠키 방식 확인

Postman의 cookie jar를 활성화하고 `POST {{authBase}}/api/auth/v1/users/no-login/guest-browser-sessions`를 Body 없이 호출하세요. 응답 `Set-Cookie`에 `guest_session`이 있어야 하며, 응답 JSON에 UUID와 세션 ID가 없어야 합니다. cookie jar가 해당 쿠키를 저장했는지 확인한 뒤 아래 요청을 실행합니다.

- `GET {{chatBase}}/api/chat/v1/chat-rooms` — `uuid` 파라미터와 Authorization 헤더 없이 호출합니다. cookie jar가 `guest_session`을 자동 첨부해야 합니다.
- `POST {{chatBase}}/api/chat/v1/chat-rooms/enter-room` — Body에 `{"roomId": <참여 중인 채팅방 ID>}`만 전달하고 쿠키로 인증합니다.
- `POST {{authBase}}/api/auth/v1/users/no-login/guest-browser-sessions/refresh` — Body 없이 호출하면 쿠키 값이 회전합니다. Postman cookie jar가 새 `Set-Cookie` 값을 저장했는지 확인합니다.
- `POST {{authBase}}/api/auth/v1/users/no-login/guest-browser-sessions/revoke` — 쿠키를 폐기하고 삭제하는지 확인합니다.

Auth 내부 `/resolve` API는 Chat 서버 간 호출에만 사용합니다. Postman이나 프런트에서 직접 호출하지 마세요. Chat의 STOMP WebSocket도 handshake에 쿠키를 자동 포함해야 하며, STOMP `CONNECT` Authorization 헤더와 메시지의 UUID/userId는 필요하지 않습니다.

## 5. 저장소별 보안 팁

### 기존 브라우저 token+uuid 방식

- 새 브라우저 구현에는 위의 HttpOnly `guest_session` 쿠키 방식을 사용하세요. 기존 `guest-sessions` JSON API는 모바일 및 기존 token+uuid 클라이언트용으로 유지됩니다.
- 기존 방식을 브라우저에서 직접 사용할 경우 발급 응답의 refreshToken이 JavaScript에 노출됩니다. BFF를 사용하지 않는다면 `localStorage`와 `sessionStorage` 모두 XSS로부터 보호되지 않는다는 점을 고려하고, XSS 방어를 우선 적용하세요.
- 토큰을 URL, 브라우저 콘솔, 앱 로그, 분석 이벤트, 오류 추적 도구, 화면 캡처에 남기지 마세요. HTTPS만 사용하세요.

### 모바일

- refreshToken은 iOS Keychain 또는 Android Keystore 기반의 보안 저장소에 보관하세요.
- guestToken은 메모리에서 사용하고 만료되면 refreshToken으로 갱신하세요.
- Chat API 요청에는 guestToken만 보내고 UUID는 저장하거나 전송하지 않아도 됩니다. 서버가 guestToken에서 UUID를 확인합니다.
- 앱 로그, 크래시 리포트, 클립보드에 토큰을 남기지 마세요.

## 6. 분실·오류 상황

| 상황 | 동작 |
|---|---|
| guestToken 만료, refreshToken 보유 | refresh API 호출 후 새 guestToken과 refreshToken을 함께 교체 |
| refreshToken 만료·폐기·유효하지 않음 | HTTP `401`. UUID만으로 복구할 수 없으므로 새 게스트 세션 생성 |
| Authorization 토큰 또는 브라우저 세션 쿠키가 누락·만료·유효하지 않음 | Chat API에서 HTTP `401` |
| refreshToken을 분실 | 기존 세션을 갱신할 수 없음. 새 게스트 세션을 생성하면 새 UUID가 발급되며 기존 채팅방 identity와 연결되지 않음 |
| 기존 게스트가 아직 유효한 guestToken과 UUID를 보유 | `POST /api/auth/v1/users/no-login/guest-sessions/upgrade`로 refreshToken 등록 가능. Authorization에 guestToken을 넣고 JSON body에 동일한 UUID를 전달 |
| 브라우저 쿠키가 없거나 세션이 만료·폐기됨 | 브라우저 세션 생성 API를 다시 호출. 절대 만료 후 생성한 세션은 새 게스트 identity |

Auth DB에는 refreshToken 원문이 아니라 해시가 저장됩니다. DB에서 세션 상태를 확인할 때도 refreshToken 원문이나 해시를 출력·공유하지 마세요. 운영 DB 대신 개발/QA DB를 사용하세요.
